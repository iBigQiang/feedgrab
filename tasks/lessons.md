# 历史教训（lessons）

> 每次收到用户修正后沉淀于此；开工前先回顾，杜绝重复犯错。

## 2026-07-06 · AI 修复"已完成"≠ 实测完成

**背景**：Codex 修复飞书视频保存 bug，单测 357 passed 后在 DEVLOG 标记"状态：已完成"，但其沙箱访问飞书被网络拦截，真实 URL 端到端从未跑通。用户实测视频依然保存不到，返工一轮。

**规则**：
1. 网络抓取/下载类功能，**必须用真实 URL 实测到产物落地**（文件存在 + 大小/结构校验）才能标记完成；单测通过只是必要条件
2. 接手他人（含 AI）声称"已完成"的修复时，先查其验证记录里有没有真实实测；没有就先实测复现，再谈下一步
3. DEVLOG"状态：已完成"必须附实测证据（产物路径、字节数、校验结果），不能只列测试计数

## 2026-07-06 · 播放器流 URL ≠ 原始文件 URL

**背景**：飞书 DOM `<video src>` 的 `/stream/download/video/{token}/` 是转码预览流（22.4MB 原件只返回 4MB），原始文件在 `/download/all/{token}/`。第一轮修复把优先级搞反。

**规则**：
1. 抓取媒体时优先找**原始文件端点**，播放器 src 只做兜底；接入前先对比下载产物与平台记录的原始 size
2. 下载响应必须校验 content-type（拒绝 text/html / application/json 错误页写成媒体文件）、拒绝 206 残片

## 2026-07-06 · 下载类功能日志必须用户可见

**背景**：`feishu.py` 用 std logging（无 handler，INFO 被吞），feedgrab 全局可见日志是 loguru。下载成功与否终端毫无动静，用户无法区分"没触发"和"失败"，加大排查成本。

**规则**：feedgrab 内所有 fetcher 日志统一用 `from loguru import logger`；新增文件时检查 import，不用 `logging.getLogger`

## 2026-07-06 · 本机 pytest 环境

**背景**：`C:\Users\Qiang\AppData\Local\Temp\pytest-of-Qiang` 权限拒绝访问，凡用 `tmp_path` fixture 的用例 setup 即 ERROR。

**规则**：本机跑 pytest 一律加 `--basetemp=.tmp/pytest-tmp`

## 2026-08-21 · 「拿到响应」≠「拿到内容」——失败态必须有名字

**背景**：`mpweixin-id` 遇微信限流 `ret=200013`，`_fetch_article_list` 把所有非 0 返回一律当成"列表读完了"（`return [], True, 0`），上层照常走完流程打印"✅ 抓取完成，总数 0"。同一个坏模式在 `evaluate_wechat_article` 重演：页面没有 `#js_content` 就把 `page.title()`（"微信公众平台"）+ `body.innerText`（"该内容已被发布者删除"）当成功结果返回，44 篇占位页因此变成空壳 md 并计入 `fetched`。

**规则**：
1. 抓取层拿到"一个响应"不等于拿到"想要的内容"。错误码分支不得与"正常结束"分支合并——限流、鉴权失败、参数错误各自抛出带原文的异常，只有真正读完才算结束
2. 平台返回的 `err_msg` 必须原样带进日志和异常，不能只留裸错误码；`freq control` 这种自解释字符串是排查的起点
3. 页面级兜底（DOM 缺失时抓 body 文本）必须先判定占位页/错误页，给失败态一个名字（如 `unavailable_reason`）让调用方分流；判定用"双条件"（标题退化 + 文案命中），漏判时退化为原行为，宁可少判不可误杀
4. 失败中断不得清理断点进度；只有"完整跑完"才清
5. 可重试的失败（风控验证页）与永久失败（内容已删除）要分开：前者不写去重索引保持可重试，后者写索引避免反复重试
6. **"这一页没有结果" ≠ "结果集读完了"**。分页终止必须依据服务端的明确信号（空 `publish_list` / `is_continue=0`），不能依据"本页解析出 0 条"——中间页可能只是没有目标类型的记录。收尾审查中我自己就用这个写法把 bug 重新引入了一次：修某类缺陷时最容易用同一类写法再犯，"是我刚写的"不是跳过审查的理由

## 2026-08-21 · 反爬限流先做边界矩阵，再谈方案

**背景**：遇到 200013 的第一直觉是"多账号轮换"（项目里 Twitter 已有成熟的 `fetch_with_cookie_rotation`）。实测换第二个微信账号同样 200013，方案当场作废。

**规则**：限流类问题先花几分钟做**边界矩阵**再动手——换目标对象 / 换账号 / 换接口版本 / 换参数取值四个维度各测一遍，同时保留一个"已知正常"的对照组（本例是"查自己的号" + searchbiz）。矩阵能直接判定配额挂在哪个维度上，省掉一轮无效实现；否决结论要写进方案文档，避免以后重走。

## 2026-08-21 · 工具链：Bash heredoc 与 Edit 会折叠反斜杠

**背景**：`cli.py` 里 emoji 写成字面转义序列 `✅`（源码中是反斜杠+u2705）。用 Edit 匹配这段时反复失败——JSON 参数层把 `\\u2705` 解析成了 ✅ 单字符；改用 Bash heredoc 写 Python 脚本，`<<'PY'` 引号形式下 `'\\u2705'` 仍被折叠成 `'✅'`（实测 `len == 1`）。

**规则**：处理含**字面反斜杠**的文件内容时，不要依赖 Edit 的 old_string 或 heredoc 里的转义写法。用 `chr(92)` 拼接反斜杠，或改用行号级替换（先 `repr()` 打印目标行确认真实字节，再按 index 替换）。

**2026-08-31 复发（写 DEVLOG 时）**：在 quoted heredoc 里写 `X\\bookmarks\\all`，被压成一层后 Python 把 `\b` 当退格转义，落盘成 `Xookmarksll` —— 肉眼看不出，grep 也搜不到。**补充规则**：(1) 文档里的 Windows 路径统一写正斜杠 `X/bookmarks/all/`，从源头消除反斜杠；(2) 任何通过脚本写文件的操作，收尾必须跑一次控制字符自检 `grep -cP '[\x00-\x08\x0b\x0c\x0e-\x1f]' <file>`，结果非 0 即为污染；(3) 看到 `SyntaxWarning: invalid escape sequence` 就说明反斜杠已被压掉一层，别忽略这条警告。

## 鉴权诊断：单次 401 不足以定性，必须做对照 + 身份反查

**踩坑**：主账号 GraphQL 返回 401，我据此判定「登录态失效」并上报。强哥当即反驳
「twitter.json 登录态是有效的啊」。虽然复测后证明文件确实失效，但我上报时的证据强度不足以
支撑这个结论 —— 只有单点观测，没有对照组，也没说清「哪个账号」。用户有理由不信。

**为什么会错**：401 有多种成因（cookie 失效 / 缺 `x-client-transaction-id` 签名头 /
ct0 与 auth_token 不配对 / 过期的 `__cf_bm`）。单跑一次分不清是哪种。

**正确做法**
1. **对照实验**：同一 header 构造、同一端点，跑完所有 cookie 槽位。若其他号 200 而目标号 401，
   唯一变量就是 cookie —— 这才排除了签名头等其他假说。
2. **身份反查**：`x.com/i/api/1.1/account/multi/list.json` 返回 `screen_name`。
   「这个槽位里到底是谁的号」往往比「有效/无效」更关键 —— 本次正是它证明了 5 个备用号
   都不是用户本人的号，书签轮换在语义上无解。
3. **换域名前缀再判 404**：`api.x.com/1.1/account/...` 已下线返 404，
   `x.com/i/api/1.1/account/...` 仍活。**404 是端点问题，不是鉴权失败** —— 我曾把备用号的
   404 误读成「登录态无效」，自我纠正后才拿到正确结论。
4. **区分浏览器端 expires 与服务端 session**：cookie `expires=2027-04` 只是浏览器过期时间，
   服务端 session 可能早已作废。别拿 expires 当有效性证据（用户也容易被它误导）。
5. **终极判据用浏览器**：加载 storage_state 打开目标私有页，看是否重定向登录页。
   浏览器带全部 cookie + 完整 JS 环境 + 自动生成 transaction id，它跳登录页 = 服务端认定未登录。

**用户反驳时的姿态**：不附和、也不硬顶。把反驳当线索去查（这次先怀疑我们自己丢了 41 个
cookie，因而发现 `build_graphql_headers` 只发 2 个 cookie 的真实缺口），拿到多重证据再定性，
同时说清用户为何会那么认为（Chrome 里确实登录着 —— 但那是 Chrome 的 cookie，不是这个文件）。

## 2026-08-31 · 工具链：Bash heredoc 写多行代码/测试文件不可靠

**背景**：想给 `tests/test_twitter_primary_account.py` 追加用例，用 `cat >> file <<'PYEOF' ... PYEOF`
直接报 `bash: -c: line 1: unexpected EOF while looking for matching ''`（exit 2），文件未被写入
（`wc -l` 仍 454 行）。这是本机 heredoc 的**第二类**失败 —— 第一类是上一条记录的"反斜杠被压掉一层"。

**规则**：**写代码和测试一律用 Write / Edit 工具**，不要用 heredoc。heredoc 只用于短小的一次性
shell 命令。若非要用 `python - <<'PY'` 写文档类文本，收尾必须做两项自检：
控制字符 `grep -cP '[\x00-\x08\x0b\x0c\x0e-\x1f]' <file>` 应为 0，
以及 `grep -n -F '<刚写入的特征片段>'` 确认正则/路径这类含反斜杠的内容没被压坏。
看到 `SyntaxWarning: invalid escape sequence` 就说明已经压掉一层，必须回头核对落盘内容。

## 2026-08-31 · 同一条策略有多个入口时，判据必须抽成一个函数

**踩坑**：给 X 的 favoriters 渠道加"必须用主账号"的闸门，我只在 `reader.py` 加了，
而且判据是写死的 `mode == "favoriters"`。CLI 的 `x-favoriters` 完全没有闸门 —— 缺主账号时
拿备用号发请求，打印"总数：0"，看起来像这条推文没人点赞。是 `/code-review` 抓到的，不是我自己想到的。

**规则**：改动涉及"要不要做某件事"的策略判断时，先问**有几个入口会走到这条策略**
（CLI / reader / service / MCP 通常各有一条），把判据抽成一个函数放在策略的定义处
（本例是 `twitter_retweeters.mode_requires_primary()` 读 `_MODE_CONFIG`），所有入口调它。
新增一个同类渠道时应该只改配置一处，而不是去每个调用点补 if。未知取值默认走保守分支。

## 2026-08-31 · 替换一层抽象前，先列清它顺手做了哪些事

**踩坑**：把多账号轮换换成"钉死主账号"（`primary_only=True`）时，只想到"不要切换账号"这一件事。
但 `load_twitter_cookies()` 内部还顺手**跳过了处于 15 分钟限流冷却的账号** —— 钉死单账号后没有
可跳的对象，这个能力静默失效：请求打出去必 429，回到上层只剩"无响应"一个信号，于是被报成
"登录态已过期"，误导用户去重新登录（实际只要等冷却）。

**规则**：替换/绕过一层现有抽象时，先把它的实现读一遍，列出它除了主职责之外还做了什么
（重试、缓存、跳过、归一化、埋点），逐条确认新路径要不要补。**尤其是错误归因**：
少了一个信号源，上层就会把 A 报成 B，用户按错误提示去操作，比直接失败更费时间。

## 2026-08-31 · 写进文档的数字，一律现场跑一遍再填

**踩坑**：DEVLOG / CLAUDE.md / AGENTS.md 三处都写了"测试 412 → 423 passed（+11）"，是凭印象填的。
实际用 `pytest --collect-only` 逐文件计数（20 + 14 + 12 = 46）+ `--ignore` 掉三个新文件跑基线
才拿到真实口径：**390 → 436**。差了 13 个用例，而且方向也不对（我以为是"追加"，其实三个文件都是新建）。

**规则**：测试数、条目数、耗时、文件数这类会写进文档的数字，**填之前现场跑一条命令拿到**，
不要从上下文记忆里回捞（迭代中途跑过的中间态数字尤其容易串）。基线数字用
`--ignore=<新文件>` 反向验证一次，比"我记得之前是 N"可靠。

## 2026-08-31 · 用户报的现象未必是缺陷本身，先验证因果链再动手

用户报「书签目录里有三个重复的 md」。听起来像去重索引失效，但查下来 `source` URL 和 `item_id`
三者各不相同、全都正确 —— 三份本就该是三条不同的书签。真正的缺陷是**内容被替换**：抓「别人在
某 thread 下的回复」时，落盘正文变成了根推作者的推文，被收藏那条的内容彻底丢失；标题跟着变成
根推的，多份撞名才触发 hash 后缀，于是**看起来**像重复。

**规则**：修之前先把「用户看到的症状 → 根因」这条因果链走通并各自实证。症状能被多种根因解释时，
按最容易证伪的那条先查。本例只要对比「文件里的 source URL」和「该 URL 推文的真实正文」，
一步就能证明是内容错位而非重复。顺带：真实缺陷的影响面往往比报告的大——这条不止影响书签，
`_fetch_via_graphql` 无条件先跑 thread，所有单条推文抓取都中招。

## 2026-08-31 · 诊断阶段的推断只是假设，下结论前先查对象的真实身份

同一个案子里，我的第一版根因是「@ClockWorkMe 转推了 @LaoVStories 的推文，URL 用了转推者的
status ID，内容用了原推的」。逻辑自洽，也能解释全部现象，但**是错的**。直接调
`fetch_tweet_by_rest_id` 查那三条推文，`是否转推` 全是 `否` —— 实际是回复，不是转推。

**规则**：涉及平台数据结构的判断（转推/引用/回复/thread），不要从产物形态倒推，直接拉一次原始
API 响应确认 `__typename`、`retweeted_status_result`、`in_reply_to_status_id` 这些字段。
一次请求的成本远低于按错误模型改代码。这与 `2026-08-31 · 反爬限流先做边界矩阵` 是同一类纪律：
**先把事实测出来，再谈方案**。

## 2026-08-31 · 写完测试要验证它真的会失败

新增 6 例线程测试后全部通过 —— 但「通过」本身不能证明测试有效，可能是断言写松了、
或 mock 掉了真正出问题的路径。做法：`git stash push <被修的文件>` 临时撤销修复再跑一遍，
确认目标用例**如期失败**（并打印出 bug 的实际表现），再 `git stash pop` 恢复。
本例撤销后目标用例返回了根推作者的线程数据、断言失败，证明测试确实卡在缺陷上。

**规则**：修 bug 配的回归测试，必须做一次「撤销修复 → 测试失败 → 恢复修复 → 测试通过」的往返，
否则不能算证明。注意 `git stash push <path>` 不动 untracked 文件，新写的测试文件会被保留。
