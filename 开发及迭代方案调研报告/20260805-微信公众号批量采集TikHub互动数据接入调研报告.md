# 微信公众号批量采集 TikHub 互动数据接入调研报告

> 调研日期：2026-08-05
> 基线版本：[feedgrab Desktop v0.1.19 20260710](https://github.com/iBigQiang/feedgrab/releases/tag/desktop-v0.1.19-20260710)
> 调研性质：只读代码与公开文档核验；未调用付费接口、未使用真实 Token、未抓取真实账号。

## 1. 结论摘要

推荐将“现有 MP 后台登录态列文章 + feedgrab 浏览器抓正文 + TikHub 仅补单篇互动数据”作为默认方案（方案 A），不要把 TikHub 文章列表作为默认主链。

原因很直接：两种方案都仍要由 feedgrab 逐篇打开文章并提取正文，速度瓶颈和正文成功率主要由这一步决定；而 TikHub 列表接口只会额外增加费用、串行分页等待和一个 `gh_username` 映射前置条件。

| 目标 | 方案 A：MP 后台列表 + TikHub stats | 方案 B：TikHub 列表 + TikHub stats |
| --- | --- | --- |
| 文章正文 | feedgrab 逐篇浏览器抓取 | feedgrab 逐篇浏览器抓取 |
| 互动数据 | TikHub 每篇 1 次 | TikHub 每篇 1 次 |
| 500 篇 API 成本 | **$5.00** | **$5.25** |
| 1000 篇 API 成本 | **$10.00** | **$10.50** |
| 相对速度 | 较快 | 较慢，额外串行列表页 |
| 相对成功面 | 依赖已验证的 MP 后台会话和文章 URL | 多一个供应商列表链路，且需 `gh_username` |
| 建议定位 | 默认生产路径 | 会话不可用时的显式备选，不应静默替换 A |

这里的美元金额仅为 TikHub API 调用费用，不含充值支付手续费、税费、汇兑和任何未证实的辅助接口费用。TikHub 对这两个目标接口的实时端点元数据标注为不享受免费额度和阶梯折扣，故不能套用其网站的通用低至 $0.001/请求宣传价。

### 2.1 当前 `mpweixin-id` 主链

1. 用户先运行 `feedgrab login wechat` 保存 `sessions/wechat.json`。
2. `mpweixin-id <公众号显示名称>` 在 MP 后台通过 `searchbiz` 精确匹配名称，得到 `fakeid`。
3. 通过 MP 后台 `appmsgpublish` 按 `begin/count/fakeid/token` 拉取历史群发，再展开每个群发中的 `appmsgex` 文章。
4. 每篇文章开新标签页，调用 `evaluate_wechat_article()` 提取正文、富文本、标题、作者、封面等，再输出 Markdown。
5. 使用 `mpweixin` 去重索引与进度文件记录批次状态。

源码证据：

- 账号精确匹配与 `fakeid`：`feedgrab/fetchers/mpweixin_account.py:87-129`
- MP 后台文章列表：`feedgrab/fetchers/mpweixin_account.py:132-189`
- 逐篇正文抓取和保存：`feedgrab/fetchers/mpweixin_account.py:320-389`
- 默认每篇延迟 3 秒：`feedgrab/config.py:710-715`、`feedgrab/fetchers/mpweixin_account.py:404-405`

### 2.2 当前互动数据的真实缺口

代码已经有 `reads`、`likes`、`wow`、`shares`、`comments` 的数据承载和 Markdown front matter 输出能力：

- 页面脚本尝试读取互动字段：`feedgrab/fetchers/browser.py:634-652, 721-745`
- Schema 透传互动字段：`feedgrab/schema.py:400-415`
- front matter 输出：`feedgrab/utils/storage.py:500-519`

但这不是可靠的批量互动数据来源。MP 后台管理登录态不等于微信文章阅读端会话；匿名页面通常不能稳定返回真实数据。可选的精选评论请求也不是互动统计，且普通浏览器或 MP 后台会话可能返回 `ret=-3 no session`。所以现有产品具备输出位，但缺少稳定、批量、可计费的互动数据提供者；TikHub 的单篇 stats 正好补这个缺口。

## 3. TikHub 两个接口的已核实事实

以下以 TikHub 官方文档与其端点信息接口在 2026-08-05 的公开元数据为准。接口价格是可变外部事实，实施前必须再次调用供应商的端点信息或价格计算接口确认。

| 项目 | 文章互动数据 | 公众号文章列表 |
| --- | --- | --- |
| 接口 | `POST /api/v1/wechat_mp/v2/fetch_article_stats` | `POST /api/v1/wechat_mp/v2/fetch_account_articles` |
| 鉴权 | `Authorization: Bearer <token>` | `Authorization: Bearer <token>` |
| 单价 | $0.01/次 | $0.01/次 |
| 免费额度 | 不适用 | 不适用 |
| 阶梯折扣 | 不适用 | 不适用 |
| 限流 | 10 请求/秒 | 10 请求/秒 |
| 超时提示 | 供应商提示设置至少 30 秒 | 供应商提示设置至少 30 秒 |
| 文档最后修改 | 2026-07-21 09:15:43 | 2026-07-21 09:15:43 |

### 3.1 `fetch_article_stats`：互动数据

官方文档：[获取公众号文章互动数据](https://docs.tikhub.io/472974852e0)。

- 请求体必填 `url`，可传公众号短链接或含 `__biz` 的长链接；可选 `raw`，默认 `true`。
- `raw=false` 的核心字段包括：`read_num`、`like_count`、`old_like_count`、`share_count`、`collect_count`、`comment_count`、`star_num`。
- 推荐的内部标准化映射：

| TikHub 字段 | feedgrab 已有字段 | 含义 |
| --- | --- | --- |
| `read_num` | `reads` | 阅读量 |
| `like_count` | `likes` | 点赞 |
| `old_like_count` | `wow` | 在看 |
| `share_count` | `shares` | 分享 |
| `comment_count` | `comments` | 评论数 |
| `collect_count` | 新增显式字段 | 收藏 |
| `star_num` | 新增显式字段 | 星标或喜欢，保留供应商原义 |

`collect_count` 与 `star_num` 不能静默丢弃，但也不能臆测为现有 `likes` 或 `wow`。应以显式新字段保存，并写入 `engagement_provider: tikhub`、`engagement_fetched_at`、`engagement_status`，使数据来源与抓取时点可审计。

### 3.2 `fetch_account_articles`：账号文章列表

官方文档：[获取公众号文章列表](https://docs.tikhub.io/472974858e0)。

- 必填的是 `username`，其语义为 `gh_...` 格式的 `gh_username`，不是 feedgrab 当前输入的显示名称，也不是当前 MP 后台流程取得的 `fakeid`。
- 可选 `page_size`，范围 10 至 20，默认 20；本文成本按最大值 20 计算。
- 首次请求不传 `offset`，后续请求必须串行回传上一页的 base64 `next_offset`，直到 `is_end` 为真。接口不自动翻页。
- `raw=false` 可获得文章 URL、标题、摘要、封面、发布时间、`app_msg_id` 等列表信息；它不提供完整 Markdown 正文。
- 官方明确提示微信服务器可能较慢，客户端 timeout 低于 30 秒可能发生“已扣费但未收到响应”。

这意味着方案 B 存在一个未闭合前置条件：当前 `mpweixin-id` 从显示名称得到的是 MP 后台 `fakeid`，而 TikHub 列表需要 `gh_username`。在未验证一个不额外收费且可靠的映射路径前，不能把该映射成本写成零，也不能承诺 B 可从现有 CLI 输入直接执行。

### 3.3 调用计费的注意事项

TikHub 通用定价页说明非 200 请求不收费，但两个微信接口文档同时警告小 timeout 可能已扣费却收不到响应。因此预算不能把客户端未收到响应当作必然免费；应按实际发出的请求次数预留重试成本，并把 provider `request_id`、HTTP 状态、耗时和本地重试编号写入运行日志。

来源：[TikHub 定价页](https://tikhub.io/pricing)、[端点信息接口文档](https://docs.tikhub.io/186826054e0)、[价格计算接口文档](https://docs.tikhub.io/186826052e0)。

## 4. 成本测算

设：

- `N` = 本次需要补互动数据的去重后文章数；
- `P = ceil(N / 20)` = TikHub 列表页数，按允许的最大 `page_size=20`；
- `R_s` = stats 额外实际请求数，例如网络重试；
- `R_l` = 列表额外实际请求数；
- 两个接口当前均为 `$0.01/请求`。

则：

```text
方案 A 成本 = $0.01 x (N + R_s)
方案 B 成本 = $0.01 x (N + P + R_s + R_l)
```

在无重试、列表每页 20 篇的理想条件下：

| 文章数 | 方案 A：stats 请求数 | 方案 A 成本 | 方案 B：列表请求数 | 方案 B：总请求数 | 方案 B 成本 | B 比 A 多付 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 500 | 500 | $5.00 | 25 | 525 | $5.25 | $0.25 |
| 1000 | 1000 | $10.00 | 50 | 1050 | $10.50 | $0.50 |

因此，对已成功通过 MP 后台列出文章 URL 的账号，完成所有互动数据的最低 API 成本是：500 篇 $5.00、1000 篇 $10.00。方案 B 的差额不大，但它确实更贵，而且不提升正文能力。

### 4.1 重试预算示例

若 1000 篇 stats 因超时额外实际发送 5% 重试，即 `R_s=50`：

```text
方案 A：$0.01 x 1050 = $10.50
方案 B：$0.01 x (1000 + 50 + 50 页 + 0 列表重试) = $11.00
```

该例只是预算模型，不是供应商成功率预测。应以运行日志和 TikHub 控制台实际扣费结算。

## 5. 两种方案的完整路径比较

### 5.1 方案 A：MP 后台列表 + feedgrab 正文 + TikHub stats

```text
MP 后台登录态
  -> searchbiz / appmsgpublish 列文章与 URL
  -> feedgrab 浏览器逐篇抓取正文、图片、元数据
  -> TikHub fetch_article_stats(url)
  -> 合并互动字段后保存 Markdown
```

优势：

- 不改变现有账号名称输入、`fakeid` 查询、去重索引、正文抓取和目录结构。
- 直接复用已列出的 `link` 调 stats，没有 `gh_username` 映射问题。
- 不收 TikHub 列表费，成本最低。
- 第三方只收到文章 URL，不需要上传 MP 后台 cookie 或 token。

限制：

- 仍依赖 MP 后台登录态；会话过期时不能枚举文章。
- 现有逐篇正文抓取是串行的，默认单篇间隔 3 秒，是总体耗时的主导因素。
- stats 的供应商可用性会影响互动字段完整度，不能影响已成功获取的正文落盘。

### 5.2 方案 B：TikHub 列表 + feedgrab 正文 + TikHub stats

```text
用户提供或先解析 gh_username
  -> TikHub fetch_account_articles 分页列 URL
  -> feedgrab 浏览器逐篇抓取正文、图片、元数据
  -> TikHub fetch_article_stats(url)
  -> 合并互动字段后保存 Markdown
```

优势：

- MP 后台会话不可用时，理论上仍有机会完成公开文章列表发现。
- 可作为独立供应商链路的容灾备选，避免把所有发现能力压在 MP 后台会话上。

限制：

- 正文仍由 feedgrab 抓取，不能减少详情抓取次数，也不改善其详情成功率。
- 列表分页需要 25 或 50 次串行请求，供应商特别提示单页可能慢。
- 每批多 $0.25 或 $0.50，还未含任何 `gh_username` 映射成本。
- 多一条第三方列表链路和一套翻页状态，失败面比 A 大。

## 6. 速度与成功率：可确认与不可确认的边界

### 6.1 速度排序

在正文量相同、且两方案均使用 feedgrab 抓详情的前提下：

```text
速度预期：方案 A > 方案 B
成本：    方案 A < 方案 B
```

这是流程结构推论，不是线上压测数据。理由是 B 必然新增 `ceil(N/20)` 次依赖 `next_offset` 的串行列表请求，而两者共有相同数量的正文和 stats 请求。

TikHub stats 最大 10 请求/秒时，500/1000 次 stats 的“发起下界”约为 50/100 秒；它不是完成时长承诺。真实时间还受单请求响应、30 秒超时、重试、供应商限流和当前 feedgrab 串行正文抓取影响。

### 6.2 成功率排序不能凭空给出

供应商公开文档未给出这两个接口的成功率、P50/P95 延迟、SLA、错误类别分布或“超时后一定不计费”的承诺。因此不能严肃地把 A 或 B 写成某个具体成功率，也不能承诺 B 比 A 更稳定。

可以确认的风险排序是：

| 维度 | 方案 A | 方案 B |
| --- | --- | --- |
| 正文失败风险 | 相同，均由 feedgrab 浏览器抓取决定 | 相同 |
| stats 失败风险 | 相同，均每篇调用一次 | 相同 |
| 列表失败风险 | MP 后台会话和内部接口 | TikHub 微信列表页，且需串行 cursor |
| 额外身份映射风险 | 无 | 有，`fakeid` 与 `gh_username` 不同 |
| 总失败面 | 较少 | 更多 |

结论：在已有有效 MP 后台登录态时，A 的预期综合完成率更好；在 MP 会话无法恢复时，B 只有在先证明 `gh_username` 可得且列表接口对目标账号可用后，才应作为备选。该结论是由依赖数量作出的工程推断，必须以小样本实测验证。

## 7. 推荐的最小接入设计

本次仅调研，不修改代码。若进入实施，建议保持现有 CLI 行为，新增显式、可关闭的 TikHub stats 补充层。

### 7.1 接入点

放在 `feedgrab/fetchers/mpweixin_account.py` 的单篇详情成功后、`from_wechat()` 和 `save_to_markdown()` 之前，即现有约 `334-362` 行之间：

```text
evaluate_wechat_article(link)
  -> normalize_tikhub_stats(link)
  -> 将可用 stats 合并到 art_data
  -> 现有标题/作者/封面 fallback
  -> from_wechat() -> save_to_markdown()
```

这样可以复用原有正文、媒体下载、去重和输出路径，不更改 `mpweixin-id` 命令名称、默认目录或 Markdown 主结构。

### 7.2 必要配置和安全边界

建议新增但默认关闭的配置：

```dotenv
TIKHUB_API_KEY=
MPWEIXIN_TIKHUB_STATS_ENABLED=false
MPWEIXIN_TIKHUB_STATS_CONCURRENCY=5
MPWEIXIN_TIKHUB_STATS_TIMEOUT_SECONDS=35
MPWEIXIN_TIKHUB_STATS_MAX_RETRIES=0
```

- Token 只能从环境变量或本地密钥存储读取，绝不写入 Markdown、日志、示例值、桌面安装包或 Git。
- 不向 TikHub 发送 MP 后台 cookie、`fakeid`、后台 token 或任何用户会话；stats 仅发送文章 URL。
- 第三方 stats 失败必须降级为“正文成功、互动字段缺失”，而非使整篇正文失败。
- 记录供应商 `request_id`、耗时、HTTP 结果、抓取时间和次数，但日志必须脱敏 Authorization header。
- `reads=0` 也应作为一个有效且可解释的值保存。现有输出逻辑以 truthy 判断 `reads`，实施时应改为区分 `None` 与 `0`，避免把真实零值误写为缺失。

### 7.3 并发与断点原则

当前正文抓取逐篇串行，不建议为追求 stats 吞吐而让多个浏览器正文页面同时高并发。推荐“正文仍串行，stats 有界并发”的队列模型：正文成功后投递 URL，stats worker 保持最多 5 并发，满足供应商每端点 10 RPS 限制并保留余量。最终落盘前等待该篇 stats 的短超时；失败则带明确状态落盘。

现有进度文件不能直接视为可靠断点续传：它在页内每篇后写 `next_begin = begin + page_size`，页中断可能跳过剩余文章；`finally` 的清理条件也会在很多非成功退出场景清除进度。进行 500 或 1000 篇批处理前，应先修复为“只在整批完整结束时清理，并保存页内文章序号或 URL 级状态”。这是可靠批量成本核算和断点恢复的前置修复，不属于 TikHub API 接入本身。

## 8. 实施前的验证门槛

先做 50 篇受控试运行，不要直接消费 500 或 1000 篇额度。

| 验收项 | 必须记录 | 建议判定 |
| --- | --- | --- |
| 正文 | URL、是否保存、正文长度、失败原因 | 与关闭 stats 的基线对比，无新增正文失败 |
| stats | HTTP 状态、`request_id`、`get_data_succ`、字段是否齐全 | 区分“接口成功但无可用数据”和请求失败 |
| 成本 | 本地实际发送次数、重试次数、TikHub 控制台扣费 | 与 `$0.01 x 实发次数` 对账 |
| 耗时 | 每篇详情耗时、stats 耗时、整体 P50/P95 | 决定 timeout 与并发，不以理论 QPS 代替 |
| 对齐 | 两套列表的 URL 交集和漏项 | 只有计划启用 B 时才必测 |
| 恢复 | 中断后重跑是否漏篇、是否重复计费 | 修复进度语义后必须通过 |

建议门槛：先要求正文保存不因 stats 失败而下降；再评估 stats 中可用互动字段的覆盖率与实际成本。只有 50 篇结果达到用户可接受覆盖率，才扩展到 500/1000 篇。

## 9. 最终排序与决策

在“文章详情和互动数据都必须具备”的既定目标下：

1. **方案 A：MP 后台列表 + feedgrab 详情 + TikHub stats**。成本最低、链路最短、与指定发布版本兼容，建议优先实施。
2. **方案 B：TikHub 列表 + feedgrab 详情 + TikHub stats**。成本略高、速度预期更慢、需要 `gh_username` 映射；只作为 MP 会话失效时的显式备选，且须先实测列表覆盖率和映射方式。

不建议“TikHub 列表替代 feedgrab 详情”作为本次需求的方案，因为公开列表接口不等于完整正文 Markdown 抓取，也不能替代 feedgrab 对富文本、图片、本地化、去重和 Obsidian 输出的现有能力。
